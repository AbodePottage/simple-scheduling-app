HTML & JSX

the document is a treeJSX is just functions

HTML is the one browser language with no logic: it's a tree of elements describing structure and meaning. Everything you see is a node in that tree (the DOM). React's JSX is a thin skin over it — markup that compiles to function calls. Learn HTML's grain first, then JSX is a five-minute delta.

The document is one big tree

The SPA mounts into a single, almost-empty HTML file. Everything else is built by JavaScript at runtime:

<!-- client/index.html (the entire page the user first downloads) -->
<body>
  <div id="root"></div>        <!-- React fills this in -->
  <script type="module" src="/src/main.tsx"></script>
</body>
// main.tsx — mount the React tree into <div id="root">
import { createRoot } from 'react-dom/client';
import { App } from './App';
createRoot(document.getElementById('root')!).render(<App />);
⚠ "Single-page app"There is exactly one HTML page. Navigating between Home/Schedule/Team/Tasks never loads a new document — JavaScript swaps what's rendered and rewrites the URL with the History API. That's what "SPA" means, and it's why App.tsx contains its own little router.

Semantic elements: tags carry meaning

Good HTML uses tags for what content is, not how it looks. The app mostly does this well — <header>, <nav>, <main>, <section>, <aside>, <button>:

<header className="hero card">
  <nav className="hero-nav" aria-label="Page sections"> ... </nav>
</header>
<aside className="team-detail-rail"> ... </aside>
Use thisNot thisBecause
<button><div onClick>Keyboard-focusable and announced as a button for free. The app correctly uses real <button>s for every card and action.
<nav><div class="nav">Assistive tech can jump to navigation landmarks.
<dl>/<dt>/<dd>two <div>sThe DetailTable uses a real description list for label/value pairs — semantically a perfect fit.

Forms and inputs: the data-entry surface

The create/edit popups are HTML forms. A few load-bearing attributes:

<label>
  <span>Title</span>
  <input value={form.title} onChange={...} required />
</label>
<select value={form.priority} onChange={...}>
  <option value="Low">Low</option>
  <option value="Medium">Medium</option>
</select>
  • Wrapping the input in <label> makes the text clickable and ties it to the field for screen readers.
  • required, type="number", min give you browser-native validation before any JS runs.
  • <select>/<option> is the native dropdown — the app uses it for priority and sort instead of building a custom widget. Less code, more accessible.
The one form gotcha that gets every backend devA native <form> has a 30-year-old default behavior: submitting it (Enter in a field, or a type="submit" button) navigates the browser — it posts and reloads the page, blowing away all your React state. In an SPA you almost never want that. So you intercept it: 
<form onSubmit={(e) => { e.preventDefault(); save(); }}>
e.preventDefault() cancels the built-in navigation so your handler runs instead. Forget it once and you'll swear the app "randomly refreshes." Every create/edit popup in this app relies on this.

Now the JSX delta

JSX looks like HTML inside TypeScript, but it's syntactic sugar: each tag compiles to a function call that returns a plain object describing the node. Five rules cover 95% of it.

1. It's expressions, not a template language

<strong>{selectedWorkItem.title}</strong>
<span>{item.durationMinutes}m</span>
<span>Showing {from}-{to} of {total} {noun}</span>

Curly braces drop you back into TypeScript. Anything that evaluates to a value can go there — variables, calls, ternaries.

2. className, not class (and camelCase attrs) ⚠ different

<div className="pagination-controls" aria-label="Pagination">

class is a reserved word in JS, so JSX uses className. Most attributes become camelCase (onClick, onChange, tabIndex). ARIA and data-* attributes keep their dashes.

3. Lists are .map(), and every item needs a key

{tasksPage.items.map((item) => (
  <button key={item.id} className="task-item" onClick={() => toggle(item.id)}>
    <strong>{item.title}</strong>
  </button>
))}
Why keys matterThe key is a stable identity React uses to tell "the same item moved" from "a different item appeared," so it can re-paint the minimum. Use the data's id — never the array index. This pattern (map rows to elements) is how every list, column, and chip in the app is rendered.

4. Conditional rendering with ? and &&

{tasksPage.total === 0 ? (
  <div className="empty-state"><strong>No work items match.</strong></div>
) : null}

{lastPage > 1 ? ( <div className="pagination-controls"> ... </div> ) : null}

There's no if inside JSX, so you use ternaries (and short-circuit &&). The empty-state and the pagination controls both appear/disappear this way. Handling the empty case in markup is a small thing the app mostly gets right — and exactly the kind of "state" backend devs forget (see S7).

5. One parent, and components return a tree

export function Pagination({ page, total, ... }: PaginationProps): ReactNode {
  if (total === 0) return null;            // a component can render nothing
  return (
    <div className="pagination">          // exactly one root element
      <span className="pagination-count"> ... </span>
      {/* ...controls... */}
    </div>
  );
}

JSX must return a single root (or a <>...</> fragment). A component is just a function: data in (props), tree out. Pagination.tsx is the app's one clean example — we dissect it as a component in S6.

Accessibility: small attributes, big payoff

The app threads ARIA through the markup, and it costs almost nothing:

<button aria-label={theme === 'light' ? 'Switch to dark mode' : 'Switch to light mode'}>🌙</button>
<button aria-current={value === page ? 'page' : undefined}>{value}</button>
<nav aria-label="Pagination">
  • aria-label gives an icon-only button a spoken name.
  • aria-current="page" tells assistive tech which pagination number is active — matching the blue highlight visually.
  • Using real <button>s means keyboard users get focus and Enter/Space activation with zero extra code.
The mental modelHTML is a tree of meaningful nodes; the browser turns that tree into pixels and an accessibility tree at once. JSX lets you build that tree with the full power of TypeScript — loops, conditionals, variables — but the output is still just HTML. Write the semantic tree first; reach for <div> only when no meaningful tag fits.

Hands-on (10 min)

  1. In the browser devtools, open the Elements panel on the Tasks page. Find the <button class="task-item"> nodes — that's the .map() output, live.
  2. Tab through the page with the keyboard only. Every card and control should highlight. That works because they're real buttons.
  3. This was built with limited HTML fluency — spot one <div> that could be a more meaningful tag, and note it for the rebuild. Relearn by redoing.
