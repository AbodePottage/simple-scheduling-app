React state & effects

UI = f(state)the three hooks

This is the slide that rewires a backend brain. The whole of React reduces to one equation:

            UI = f(state)

The screen is a pure function of your data. You never imperatively poke the DOM ("set this text", "hide that row"). You change state, and React re-runs your component functions to produce a new tree, then patches only the differences onto the page. Master that inversion and the rest is vocabulary.

A component is a function: props in, tree out

Pagination.tsx is the app's cleanest component — the perfect specimen:

interface PaginationProps {        // its inputs, fully typed
  page: number;
  total: number;
  noun: string;
  onPageChange: (page: number) => void;   // a callback prop
}

export function Pagination({ page, total, noun, onPageChange }: PaginationProps) {
  if (total === 0) return null;            // render nothing
  const lastPage = Math.max(1, Math.ceil(total / pageSize));
  return ( <div className="pagination"> ...buttons... </div> );
}
  • Props are the function's arguments — data flows down from parent to child.
  • It owns no app state. Give it the same props, get the same markup. That's what makes it reusable on both the Tasks page and the two Team columns.
  • Events flow up via callback props: the child doesn't know what changing the page means; it just calls onPageChange(n) and lets the parent decide.
Data down, events upThis one-way flow is React's core discipline. Parents pass data down as props; children report events up as callbacks. The parent (App) passes onPageChange={setTasksPageNum} — so clicking "2" in the child calls the parent's state setter. (Everything routes through App here because the app is a monolith; the rebuild distributes it.)

Hook 1 — useState: memory that triggers re-renders

A component function runs from scratch on every render, so it can't use normal variables to remember things. useState is React-managed memory:

const [tasksPageNum, setTasksPageNum] = useState<number>(1);
const [theme, setTheme] = useState<Theme>(() => localStorage.getItem('theme') || 'light');
const [data, setData] = useState<BootstrapResponse | null>(null);

It returns the current value and a setter. Calling the setter is the only way to change the screen — setTheme('dark') both stores the new value and tells React to re-render. ⚠ different You do not assign theme = 'dark'; that wouldn't repaint anything. The app holds ~20 such state slices in App — selection, editing, forms, drag state, and the pagination numbers.

Hook 2 — useMemo: derive, don't duplicate

Some values are computed from state. Recomputing them every render is wasteful, and you want them recalculated only when their inputs change. The pagination query params are a textbook case:

const taskQueryParams = useMemo(() => {
  const params = { page: tasksPageNum, pageSize: 10, sort: taskSort, status: 'all', ... };
  if (taskDimension === 'status' && ...) params.status = taskFilterValue;
  else if (taskDimension === 'priority' && ...) params.priority = taskFilterValue;
  return params;
}, [tasksPageNum, taskSort, taskDimension, taskFilterValue]);  // ← dependency array

The array at the end lists the inputs. React reruns the function only when one of them changes; otherwise it hands back the cached value. Think of it as a derived column that recomputes on input change — a concept you already know from views and computed properties.

Hook 3 — useEffect: sync with the outside world

Rendering is pure, but real apps must do impure things: fetch data, read localStorage, set the document title. useEffect runs after render, and re-runs when its dependencies change. The initial bootstrap load:

useEffect(() => { void load(); }, []);   // empty deps → run once, on mount

And the heart of server-side pagination — refetch the Tasks slice whenever the query changes:

useEffect(() => {
  let cancelled = false;
  void fetchWorkItems(taskQueryParams).then((result) => {
    if (cancelled) return;                       // ignore a stale response
    setTasksPage(result);
    if (result.page !== tasksPageNum) setTasksPageNum(result.page);  // server clamped
  });
  return () => { cancelled = true; };            // cleanup runs before the next effect
}, [taskQueryParams, data]);
Three things this tiny effect teaches (1) Dependencies are a contract: the array [taskQueryParams, data] says "re-fetch when the filters change, or when the bootstrap reloads after a mutation." Get this list wrong and you get stale screens or infinite loops — the #1 React beginner bug. (2) The cancelled flag guards against a race: if the user clicks fast, an older request must not overwrite a newer one. The returned cleanup function flips the flag. (3) Trust the server: if the API clamped ?page=999 down to the real last page, the client syncs to the corrected number.

Controlled inputs: the form is state

In React, an input's value comes from state and changes through state — a round trip:

<input value={form.title}
       onChange={(e) => setForm({ ...form, title: e.target.value })} />

The input shows form.title; typing fires onChange, which sets new state, which re-renders the input with the new value. The screen and the data can never drift apart because the data is the source. ⚠ different There's no "read the field on submit" — you already have the value in state the whole time.

Putting it together: one full interaction

Click "2" on the Tasks pager. Watch the equation turn:

1. Click → Pagination calls onPageChange(2) → setTasksPageNum(2)   [useState]
2. State changed → App re-renders
3. taskQueryParams recomputes (page now 2)                        [useMemo]
4. Its value changed → the fetch effect re-runs                   [useEffect]
5. fetchWorkItems → GET /api/work-items?page=2 → setTasksPage(...)
6. State changed → App re-renders → new rows + "Showing 11-20 of 60"

No DOM surgery anywhere. State changed; the screen followed. That is the entire game.

Where the monolith strains this model

Because all ~20 state slices live in one App function, every keystroke in a form re-runs the whole component (React is fast enough that it doesn't matter here, but it's a smell). And state that should be local to a form or a page is hoisted to the top, tangling concerns.

Relearn by redoingThe fix is colocation: state lives in the smallest component that needs it. A <WorkItemForm> owns its own form state; a <TasksPage> owns its own pagination state. Data still flows down, events still flow up — but the blast radius of any change shrinks to one file. That's the central refactor of S8, and you'll only appreciate why after having lived in the one-big-component version.
The mental modelUI = f(state). Hold the truth in useState; derive from it with useMemo; reach outside with useEffect (and mind the dependency array). Pass data down as props, send events up as callbacks. Never touch the DOM — change state and let React reconcile.
