Angular: a direct translation

same scheduling appsame conceptsAngular 17+

S4–S6 taught React: components as functions, JSX, hooks, the data-down/events-up discipline. Every one of those concepts has a direct Angular equivalent. This slide is a side-by-side translation of the same scheduling app code — same logic, same domain types, different syntax and framework conventions. Read it after S6 and you can switch frameworks with a week of syntax adjustment rather than a month of relearning.

Angular versionAll examples use Angular 17+ standalone components and the new @if / @for control-flow syntax. Older Angular code uses NgModules and *ngIf / *ngFor structural directives — the concepts are the same, the syntax is more ceremonial. If you are reading a pre-2024 Angular codebase, the table at the end of section 3 maps between old and new syntax.

1. One component, three files (vs one .tsx)

React keeps everything in one file. Angular splits a component into (usually) three files by convention. The content is identical; the organisation is enforced by the framework rather than a folder convention you choose yourself.

React — one file 
// Pagination.tsx
export function Pagination({
  page,
  total,
  pageSize,
  noun,
  onPageChange,
}: PaginationProps) {
  /* JSX + logic in one place */
}
Angular — three files 
pagination.component.ts   // the class
pagination.component.html // the template
pagination.component.css  // scoped styles

Angular also generates a .spec.ts test file. The ng generate component pagination CLI command creates all four.

Styles are scoped by defaultAngular emulates CSS scoping automatically via ViewEncapsulation.Emulated. A rule in pagination.component.css only applies inside that component — what the rebuild achieves with CSS Modules, Angular gives you without opting in. The design-token pattern from S5 (:root custom properties) works identically in both frameworks.

2. The component class vs the component function

A React component is a function. An Angular component is a class decorated with metadata. Everything the function's closure holds (props, local state, derived values) the class holds as properties, getters, and methods.

React 
export function Pagination({
  page,
  total,
  pageSize = 10,
  noun,
  onPageChange,
}: PaginationProps) {

  const lastPage =
    Math.max(1, Math.ceil(total / pageSize));

  if (total === 0) return null;
  return (
    <div className="pagination">...</div>
  );
}
Angular 
@Component({
  standalone: true,
  selector: 'app-pagination',
  templateUrl: './pagination.component.html',
  styleUrls: ['./pagination.component.css'],
})
export class PaginationComponent {
  @Input() page: number = 1;
  @Input() total: number = 0;
  @Input() pageSize: number = 10;
  @Input() noun: string = '';
  @Output() pageChange =
    new EventEmitter<number>();

  get lastPage(): number {
    return Math.max(
      1, Math.ceil(this.total / this.pageSize)
    );
  }
}
  • @Component is the .NET [Attribute] pattern. It provides metadata: the HTML tag name (selector), the template file, and the styles. Angular reads this at startup, not at runtime per-render.
  • standalone: true is the modern Angular default (17+): no NgModule required. You import the class directly where you need it, like a React component.
  • @Input() is a prop. @Output() + EventEmitter is a callback prop. The data-down/events-up discipline from S6 is the same — Angular just makes it explicit with decorators.
  • Getters replace useMemo for derived values that depend only on @Input() properties. For derived values that depend on Signals, use computed() (covered in section 4).

3. Template syntax vs JSX

JSX puts markup inside TypeScript. Angular keeps them separate: the template is an HTML file with Angular-specific syntax. Compare the Pagination template with the JSX from S4:

<!-- pagination.component.html (Angular 17+) -->
@if (total > 0) {
  <nav class="pagination" aria-label="Pagination">
    <span class="pagination-count">
      Showing page {{ page }} of {{ lastPage }} {{ noun }}
    </span>
    @for (p of pages; track p) {
      <button
        [attr.aria-current]="p === page ? 'page' : null"
        (click)="pageChange.emit(p)"
      >{{ p }}</button>
    }
  </nav>
}

4. State: Signals vs useState

Angular 17 stabilised Signals — a reactive primitive that works almost identically to useState. Before Signals, Angular used plain class properties and relied on its change-detection engine to track mutations. Signals are the recommended modern path and the one to learn first. Traditional class properties still work and appear in all pre-2024 code.

React 
// declare:
const [theme, setTheme] =
  useState<Theme>('light');
const [data, setData] =
  useState<AppState | null>(null);

// read:
return <div className={theme}>...</div>;

// update:
setTheme('dark');
setData(newState);
Angular (Signals) 
// declare (class property):
theme = signal<Theme>('light');
data = signal<AppState | null>(null);

// read (template):
<div [class]="theme()">...</div>

// update:
this.theme.set('dark');
this.data.set(newState);

Reading a Signal always requires calling it as a function: this.theme(), not this.theme. Angular tracks the read and knows to re-run anything that depends on it when the value changes.

Derived state: computed vs useMemo

React 
const openItems = useMemo(
  () =>
    data?.workItems
      .filter(i => i.status === 'unscheduled')
      .length ?? 0,
  [data]   // ← dependency array
);
Angular 
openItems = computed(
  () =>
    this.data()?.workItems
      .filter(i => i.status === 'unscheduled')
      .length ?? 0
  // no dependency array — tracked automatically
);
No dependency arraycomputed() tracks which Signals were read during its last execution and re-runs automatically when any of them change. You cannot forget a dependency or include a stale one. This is one place the Angular signal model is genuinely less error-prone than React hooks.

5. Lifecycle: ngOnInit / effect vs useEffect

React's useEffect covers the entire lifecycle with one function and a dependency array. Angular separates the cases into named lifecycle hooks and — with Signals — a reactive effect().

React 
// once on mount:
useEffect(() => {
  void load();
}, []);

// when deps change:
useEffect(() => {
  let cancelled = false;
  fetchWorkItems(params).then(r => {
    if (!cancelled) setTasksPage(r);
  });
  return () => { cancelled = true; };
}, [params, data]);

// cleanup on unmount:
useEffect(() => {
  const id = setInterval(poll, 30_000);
  return () => clearInterval(id);
}, []);
Angular 
// once on mount:
ngOnInit() {
  this.load();
}

// when a Signal changes (in constructor):
constructor() {
  effect(() => {
    const p = this.taskQueryParams();
    this.workItemsService.query(p)
      .subscribe(r => this.tasksPage.set(r));
  });
}

// cleanup on unmount:
ngOnDestroy() {
  clearInterval(this.pollId);
}
React useEffect patternAngular equivalentWhen
useEffect(fn, []) ngOnInit() Run once on mount
useEffect(fn, [deps]) effect() (reads Signals inside) or ngOnChanges() (for @Input changes) Run when something changes
Cleanup return ngOnDestroy() Unsubscribe, clear timers, release resources
The cancelled-flag pattern in AngularThe React cancelled-flag pattern from S6 — let cancelled = false; return () => { cancelled = true; } — exists to handle the case where a component unmounts before an async call returns. In Angular the idiomatic equivalent is storing the Observable subscription in a property and calling this.sub.unsubscribe() in ngOnDestroy(), or using takeUntilDestroyed() from @angular/core/rxjs-interop to close the subscription automatically when the component is destroyed.

6. Services + DI vs Custom Hooks

React extracts reusable logic into custom hooks. Angular uses injectable services — classes registered in a DI container and injected wherever needed. For a .NET developer, this is the most immediately familiar pattern in the entire framework.

React (custom hook) 
// useWorkItems.ts
export function useWorkItems(
  params: WorkItemQuery
) {
  const [page, setPage] =
    useState<Page<WorkItem> | null>(null);

  useEffect(() => {
    let cancelled = false;
    fetchWorkItems(params).then(p => {
      if (!cancelled) setPage(p);
    });
    return () => { cancelled = true; };
  }, [params]);

  return page;
}

// in a component:
const page = useWorkItems(params);
Angular (injectable service) 
// work-items.service.ts
@Injectable({ providedIn: 'root' })
export class WorkItemsService {
  private http = inject(HttpClient);

  query(
    params: WorkItemQuery
  ): Observable<Page<WorkItem>> {
    return this.http.get<Page<WorkItem>>(
      '/api/work-items', { params }
    );
  }
}

// in a component:
private svc = inject(WorkItemsService);
page = toSignal(this.svc.query(this.params));

The .NET analogy is exact:

7. The RxJS callout

The one genuinely new concept: ObservablesAngular's HttpClient returns Observables from the RxJS library, not Promises. An Observable is like a Task<T> that can emit multiple values over time and compose with operators (map, switchMap, combineLatest, debounceTime). For simple one-shot HTTP calls you can bridge to a Promise: firstValueFrom(this.http.get(...)). Or convert to a Signal: toSignal(this.http.get(...)). Idiomatic Angular uses Observables throughout; the async pipe in templates subscribes and unsubscribes automatically. RxJS is powerful and has its own learning curve — it is the one part of Angular with no close .NET equivalent. Budget time for it.

The takeawayThe concepts are the same. Components receive data, render markup, raise events, fetch from the server, and clean up after themselves. Angular externalises the template, makes DI first-class, and uses decorators where React uses function arguments. Once you can read one you can read the other — the vocabulary is a week's work, not a month's. The FW slide helps you choose; this slide helps you switch.
