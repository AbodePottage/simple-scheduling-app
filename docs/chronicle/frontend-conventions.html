The client: React at scale

three kinds of statecustom hookslint · test · validate

The server now owns the data truth. This is build phase two: the client, rebuilt to mirror that server cleanly. First the mental model a backend engineer is missing — the three kinds of state — then the conventions production React codebases converge on to stay maintainable as they grow. The conventions are drawn from two well-regarded starters worth reading end to end — startercraft (an opinionated, scalable boilerplate) and react-ts-base (a typed-React concept primer). Each answers a question the monolith never had to: where does this code live, and how do we keep it from rotting?

First, the mental model: three kinds of state

Backend engineers conflate all state into "the data." On the client there are three distinct kinds, and the POC's mistake was cramming all three into useState inside one 1,803-line App.tsx.

KindExample hereWhere it belongs
Server statework items, resources, bookingsA server-state cache (TanStack Query), not raw useState
UI statewhich modal is open, dark mode, drag-in-progressLocal useState in the nearest component
URL statecurrent route, page number, active filterThe URL itself, so a link is shareable and back works
Seen in the wild: reinventing URL state, badlyA later feature needed "click this stat tile on the home page, land on /tasks pre-filtered to Open" and "click this other one, land on /schedule scrolled to the board." The table above already says that's URL state — a route and a query param, done. What actually got built first was a pendingScrollId piece of React state plus a useEffect that watches for the target page to mount and then fires the scroll, racing the navigation. It works, but it's strictly worse than /tasks?status=open and /schedule#board: it isn't shareable, it doesn't survive a refresh, and there's a race condition to reason about that URL state doesn't have. Knowing the concept and reaching for it under time pressure are different skills — this table is easy to nod along to and still skip in the moment.

The POC also mutates on the server then refetches the entire world (/api/bootstrap) on every change. In .NET terms that is invalidating your whole output cache on every write. The fix is scoped cache keys — the client mirroring the server's contract instead of re-pulling all of it:

// features/tasks/useWorkItems.ts — the shape you're aiming for
export function useWorkItems(params: WorkItemQuery) {
  return useQuery({
    queryKey: ['work-items', params],          // the cache key
    queryFn: () => fetchWorkItems(params),     // your existing api.ts helper
  });
}
Two more non-negotiablesDecompose: one component, one file, one job — per-feature folders (home/schedule/team/tasks), a router-only App.tsx. Handle every async branch: loading, error, empty, and data — the four-state machine the POC only half-built. And scope styles with CSS Modules, keeping one global tokens.css. The eight conventions below are how you get there.
Seen in the wild: the cost of no component boundaryThe top nav got redesigned four times in one evening: pill tabs → a hamburger dropdown → pill tabs again with a separator → removed entirely once its job moved onto three labeled links. Every one of those was a direct edit to App() itself, because there was no <TopNav> to edit instead. Each reversal left its own debris in the shared file — a CSS class no longer referenced by any JSX, a navItems array nothing read anymore, an import (Fragment) only the dropdown version had needed — and finding it meant grepping the whole app, not reading one component's diff. Four redesigns of an actual <TopNav> would have been four small, self-contained diffs, and "did I leave anything behind" would have been answered by that one file's own git history.

1. Custom hooks: your own reusable stateful logic

The built-in hooks are primitives. The real abstraction is that you write your own hooks by composing them — any function named useX that calls other hooks. This is the single tool the POC lacked: all its logic was inlined in App, so nothing was reusable. A custom hook is the front end's version of extracting a service.

// features/tasks/useWorkItems.ts — logic lifted out of the component
export function useWorkItems(params: WorkItemQuery) {
  const [page, setPage] = useState<Page<WorkItem> | null>(null);
  const [status, setStatus] = useState<'loading' | 'error' | 'ready'>('loading');

  useEffect(() => {
    let cancelled = false;
    setStatus('loading');
    fetchWorkItems(params)
      .then((p) => { if (!cancelled) { setPage(p); setStatus('ready'); } })
      .catch(() => { if (!cancelled) setStatus('error'); });
    return () => { cancelled = true; };
  }, [params]);

  return { page, status };          // the component just consumes this
}
// the component shrinks to presentation:
function TasksPage() {
  const { page, status } = useWorkItems(query);
  if (status === 'loading') return <Spinner />;
  if (status === 'error')   return <ErrorState />;
  return <TaskList items={page!.items} />;
}
Why this is the keystone conventionMove the fetching, the flags, and the effect into useWorkItems, and the same logic is reusable, testable in isolation, and the component becomes a thin view. Do this consistently and the 1,803-line App dissolves into a dozen small hooks and a dozen small views. In production you'd back this with TanStack Query (the React standard for server state) so caching, loading, and error come for free.
Seen in the wild: what skipping this costsMulti-select filtering was needed on two pages — Schedule and Tasks — and got built twice: taskDimensionOptions/taskValueOptions for one, backlogDimensionOptions/backlogValueOptions for the other, near-identical logic typed out a second time rather than extracted once. A useWorkItemFilters() hook, written the first time and imported the second, would have made the two pages provably consistent instead of "hopefully I copied it right" — and a bug fixed in one place would be fixed everywhere it's used.

2. The view-model split: logic apart from presentation

Push the hook idea one step and you get the convention startercraft bakes into every component: a view file that is pure JSX and a view-model (a hook) that holds the state and handlers. It is the same separation of concerns you reach for in MVC/MVVM — the view binds, the model decides.

3. useReducer + Context: when useState outgrows itself

The POC holds ~20 useState slices in one component and threads values through deep prop chains. Two standard tools fix each half of that pain:

useReducer — a state machine you already know

When several pieces of state change together by a few well-defined actions, a reducer is clearer than a fistful of setters. It is the exact (state, action) => state function you'd write on the backend.

function reducer(s: FormState, a: Action) {
  switch (a.type) {
    case 'set': return { ...s, [a.field]: a.value };
    case 'reset': return initial;
  }
}
const [form, dispatch] = useReducer(reducer, initial);
Context — dependency injection for the tree

For truly cross-cutting state (theme, current user) that many components need, Context lets a provider supply a value to its whole subtree — no prop drilling. Treat it like a registered singleton, not a dumping ground.

const ThemeContext = createContext<Theme>('light');
// provide once near the root:
<ThemeContext.Provider value={theme}> ... </ThemeContext.Provider>
// consume anywhere below:
const theme = useContext(ThemeContext);
Reach for these in orderDefault to local useState in the smallest component. Promote to useReducer when the transitions get complex. Promote to Context only for state that is genuinely global. Skipping straight to "put everything in Context" recreates the monolith's god-object in a new shape.

4. Co-locate everything a component owns

The scalable file convention isn't just "a file per component" — it's a folder per component that keeps the view, its test, its scoped styles, its types, and its logic side by side, with a barrel index.ts as the public door:

components/elements/WorkItemForm/
├── WorkItemForm.tsx            # the view
├── WorkItemForm.view-model.ts  # the hook: state + handlers
├── WorkItemForm.module.css     # styles scoped to this component
├── WorkItemForm.types.ts       # its props + local types
├── WorkItemForm.spec.tsx       # its test, right next to it
└── index.ts                    # export { WorkItemForm }  — the only public surface
Why co-location beats grouping by typeWhen everything a component needs lives in one folder, you delete the folder to delete the feature, and a change touches one place. The opposite (all CSS in /styles, all types in /types) scatters a single change across the tree — the same force that made the POC's edits sprawl. The index.ts barrel means callers import from the folder, not its internals, so you can refactor inside freely.

5. Path aliases: kill the ../../../ imports

Deep relative imports are brittle and unreadable. Both starters map alias prefixes to folders once, so every import is absolute and stable:

// tsconfig.json                         // vite.config.ts mirrors these
"paths": {
  "@features/*": ["./src/app/features/*"],
  "@components/*": ["./src/app/components/*"],
  "@hooks/*": ["./src/app/hooks/*"]
}
// then, anywhere:
import { Pagination } from '@components/Pagination';   // not '../../../components/Pagination'

Configure the same aliases in tsconfig.json (so the type-checker resolves them) and in vite.config.ts (so the bundler does). It's the JS answer to a project reference: a name that doesn't break when you move a file.

6. Lint, format, and a single validate gate

The type gate is one; production frontends add two more, then bundle all three into one command. This is the DX backbone of both reference repos.

ToolCatches.NET analogue
ESLintLikely bugs and bad patterns: missing effect deps, unused vars, rules-of-hooks violations.Roslyn analyzers
PrettierFormatting — runs automatically so nobody argues about it in review.dotnet format / EditorConfig
tsc --noEmitType errors the bundler skips.The compile step
 
// package.json — one gate that CI and you both run
"scripts": {
  "validate": "tsc --noEmit && eslint . && vitest run"
}
One green checkmarknpm run validate = types sound + lint clean + tests pass, in one command. Wire it into CI and a pull request is either green or it isn't — the same confidence a clean dotnet build + test run gives you today. An eslint-plugin-react-hooks rule would have flagged dependency-array mistakes before runtime.

7. Frontend tests assert behavior, not implementation

S8 says "tests in CI" but never shows a UI test. The standard is Vitest (the runner) plus React Testing Library (RTL), whose guiding rule is: test what a user sees and does, not the component's internals. You query the rendered output the way a person or a screen reader would — by role and text — then simulate an interaction and assert on the result.

// Pagination.spec.tsx — the app's cleanest component is the easiest to test
import { render, screen } from '@testing-library/react';
import userEvent from '@testing-library/user-event';

test('reports the page the user clicked', async () => {
  const onPageChange = vi.fn();
  render(<Pagination page={1} total={60} pageSize={10} noun="tasks" onPageChange={onPageChange} />);

  await userEvent.click(screen.getByRole('button', { name: '2' }));

  expect(onPageChange).toHaveBeenCalledWith(2);   // the contract, not the DOM internals
});
Why query by roleFinding the button by its accessible role and name (not a CSS class or test id) means the test passes only if the control is actually reachable — so your tests double as a light accessibility check. It also survives refactors: rename a class, restructure the markup, and the test still holds as long as the user-facing behavior is intact. That is the opposite of brittle snapshot tests.
Seen in the wild: verification that doesn't outlive the sessionA single evening of polish on this app produced well over a dozen one-off browser scripts — launch the dev server, click through a flow, assert on a computed style or a URL, print the result, done. Every one of them proved the fix worked at that moment. None of them persisted, so none of them protect against the next change quietly breaking the same thing. That's the gap this section is naming: the exact same effort, spent against Vitest + RTL instead of a throwaway script, leaves behind a regression suite instead of nothing.

8. Scaffold for consistency

Once a component has six prescribed files, creating them by hand is error-prone. Both starters ship a generator (npm run generate) that stamps out the folder, the barrel, and a passing test from a template. It is a small DX investment that makes the right structure the easy structure — the cheapest way to keep a growing codebase uniform.

The mental modelArchitecture (S9) decides the boundaries; these conventions decide the day-to-day texture. Extract logic into custom hooks, split view from view-model, co-locate what changes together, alias away brittle paths, and put lint + types + tests behind one gate. None of it is exotic — it's the same modularity, DI, and CI discipline you already practice on the backend, wearing front-end clothes. Apply them as you rebuild and the second app simply cannot become the first.

Read these next (15 min each)

  1. Skim startercraft's folder layout and its generate script — see the co-location and view-model split in a real tree.
  2. Skim react-ts-base's useReducer, useRef, Context, and generic-component examples — the typed-React vocabulary, isolated.
  3. In the rebuild, pick one feature and apply all eight: hook + view-model + co-located folder + alias + a test + a green validate. That one feature becomes your template.
The whole pointYou shipped a rough thing, read its scars, learned the three browser languages from real code, then rebuilt it deliberately — the server, then the client here — knowing exactly why each clean choice matters, because you felt the cost of its absence and reviewed every line that fixed it. That's the method: learn by doing, relearn by redoing, and review every diff. Now go build the second one — the real UI — and it simply cannot become the first.
