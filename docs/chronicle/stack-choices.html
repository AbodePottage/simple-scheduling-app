Stack choices

ExpressVitetsxREST

The FW slide asked which UI framework to use. This slide asks the quieter questions: why Express and not something faster? Why Vite? Why TypeScript on the server at all? And is there an alternative to duplicating types between client and server? Each tool was chosen for a reason — and each has a better alternative worth knowing before the rebuild starts.

1. Express

Express has been the default Node.js web framework since 2010. It is minimal (a router and a middleware chain — nothing else), unopinionated, and has the largest ecosystem of any Node framework. It is fine for this project. It is not what you would reach for in a new project today.

FrameworkWhat it isWhen to use it
Express (current) Minimal router + middleware. No opinions on anything. Learning, legacy projects, anything that already uses it
Fastify 2–3× faster than Express, TypeScript-first, JSON-schema validation built in, plugin system. New Node.js projects — the clear "Express but better" default
NestJS Decorators, built-in DI, modules, guards, pipes — Angular for backends. Uses Express or Fastify underneath. When you want your Node server to feel like ASP.NET Core. The most natural choice for a .NET developer going full Node.
Hono Ultra-light, runs on edge runtimes (Cloudflare Workers, Deno Deploy, Bun) as well as Node. APIs that need to run globally near users, not on a single VPS
The thing nobody says out loudYou do not have to use Node for the server at all. Your real project could use ASP.NET Core as the API and React (or Angular) as the client. They communicate over HTTP. The frontend has no idea what language the backend is written in — it only sees JSON. The Express server in this chronicle exists purely for convenience: one language, one repo, one npm run dev command. It is not a requirement. A .NET team building a frontend can keep their existing .NET backend and add a React client on top.

2. Vite

Vite is the tool that compiles and serves the React client. It has effectively won the "front-end build tool" category for new projects. You do not need to evaluate alternatives here, but you need to know the history to understand the ecosystem you are reading about.

ToolStatusNotes
Vite (current) Industry standard for new projects Dev server uses esbuild (fast, type-strips only). Production build uses Rollup. Does not type-check — that is why npm run typecheck exists as a separate step.
Create React App Deprecated (2023) Was the React default for years. Used webpack under the hood. Slow, hard to configure. Ignore it for new projects — but you will see it in old codebases.
webpack Legacy; still running most of the web Still in 60%+ of production apps because of inertia. Extremely configurable, extremely slow. Don't start new projects in it.
Turbopack Emerging — used inside Next.js Rust-based webpack successor from Vercel. Very fast, but not production-stable as a standalone tool yet.
Vite does not type-checkThis surprises .NET developers. dotnet build always type-checks. Vite does not — it uses esbuild, which strips TypeScript syntax as fast as possible without verifying it. A React build can succeed with type errors in it. The solution is npm run typecheck (which runs tsc --noEmit on both client and server). In a real CI pipeline, typecheck runs as a gate before the build step.

3. tsx (the server runner)

In development, the server is not compiled — it is run directly from TypeScript source using tsx watch. tsx uses esbuild to strip types and pass plain JavaScript to Node. It does not type-check; it just makes TypeScript files runnable instantly, like dotnet run but without the compile step.

RunnerHow it worksWhen to use
tsx (current) esbuild strips types, Node runs the JS. Fast. No type-checking. Dev servers where you want instant restarts
ts-node The original TS runner. Uses tsc to transpile. Slower, but can be configured to type-check. When you want the runner to catch type errors at startup
Bun A whole new JS runtime (like Node but faster). Runs TypeScript natively with no loader at all. New projects that can adopt Bun's ecosystem; drops in for tsx watch without code changes

4. REST — and why tRPC solves the type-duplication problem

The app exposes a REST API. The client calls GET /api/work-items and receives JSON. The types on the server (server/src/domain.ts) and the types on the client (client/src/types.ts) are manually kept in sync — a known debt. This drift risk is one of the first things the rebuild fixes (via a shared/ package).

There is an alternative pattern that eliminates the problem entirely: tRPC.

REST (current approach)
  • Server defines routes: GET /api/work-items
  • Returns JSON; client deserialises it
  • Types must be duplicated or shared via a package
  • Any mismatch is a runtime bug, not a compile error
  • Works with any client (mobile, other backends, curl)
tRPC (the alternative)
  • Server defines typed procedures: workItems.list(params)
  • Client calls them: trpc.workItems.list.useQuery(params)
  • Types flow end-to-end automatically — no duplication
  • Mismatches are caught at compile time, in your editor
  • Works only when both client and server are TypeScript

tRPC has first-class adapters for TanStack Query (the client-side data layer in the rebuild). The domain.ts vs types.ts problem literally does not exist in a tRPC project — the router type is the single source of truth for both sides.

When to use whichREST if the API must be consumed by non-TypeScript clients (mobile apps, other teams, third parties). tRPC if the only client is your own TypeScript frontend. Many products start with tRPC for the internal API and add REST endpoints only where external access is needed.

5. What the code itself teaches

Beyond the framework choices, several patterns in the POC code are worth examining closely because they illustrate concepts you will re-encounter everywhere:

The cancelled flag in useEffect

useEffect(() => {
  let cancelled = false;
  fetchWorkItems(params).then(r => {
    if (!cancelled) setTasksPage(r);   // guard here
  });
  return () => { cancelled = true; }; // set when component unmounts
}, [params, data]);

This is the JavaScript equivalent of CancellationToken in async .NET methods. If the component unmounts before the fetch completes — because the user navigated away — the return function runs, sets cancelled = true, and the .then callback does nothing. Without this guard, you get a React warning about setting state on an unmounted component and potentially a race condition where stale data overwrites fresh data. React 18's <StrictMode> deliberately mounts and unmounts components twice in development specifically to surface this kind of bug.

The Vite proxy in vite.config.ts

server: {
  proxy: { '/api': 'http://localhost:3001' }
}

In development, the React client runs on localhost:5173 and the Express server runs on localhost:3001. Without the proxy, every fetch('/api/...') call would be a cross-origin request and fail the browser's CORS check. The proxy makes Vite's dev server transparently forward any /api request to Express — from the browser's perspective, both are on the same origin. In production there is no proxy because Express serves the compiled React static files directly and handles /api itself. This is a standard pattern you will see in essentially every Node + Vite project.

buildQuery() in api.ts

function buildQuery(params: Record<string, unknown>) {
  const q = new URLSearchParams();
  for (const [k, v] of Object.entries(params)) {
    if (v !== undefined && v !== '' && v !== 'all') {
      q.set(k, String(v));
    }
  }
  return q.toString();
}

This is input sanitisation at the API call boundary — the client-side equivalent of what Zod does at the server boundary in the rebuild. The sentinel value 'all' (meaning "no filter") is stripped before the request is sent so the server does not receive it as a filter value. Small function, important concept: clean your data at every boundary, not just on one side.

In-memory state and single-threadedness

The entire app state is one JavaScript object in RAM. Every server restart loses all data. Every parallel request reads and writes the same object with no locking. A .NET developer's first instinct is to worry about race conditions — but Node.js runs your JavaScript on a single thread. Two requests cannot truly interleave the way they would in a multi-threaded ASP.NET Core process. The "restart loses data" problem is very real; the "concurrent mutation" problem is less dangerous than you'd expect. The rebuild fixes the first problem with SQLite and the Repository pattern.

The rebuild addresses all of thisS8–S10 lay out the plan: SQLite replaces in-memory state, a shared/ package eliminates type duplication, TanStack Query replaces manual useEffect fetches (and handles the cancellation problem automatically). The tools change; the concepts you learned here stay.
