The server: clean architecture & DDD

four layersa rich domainbackend-first

The prior slide set the brief, the method, and the ordered plan. This is build phase one in depth: the server, rebuilt with clean architecture and domain-driven design. You start here because it is your home turf — lock the data truth and the contract first, and the client has a stable thing to talk to.

The server: four layers, dependencies pointing inward

The POC server is one scheduling.ts — seed data, a mutable global, and all the logic in one file. In DDD terms it is a transaction script over a shared global. Clean architecture is the same onion you know from .NET: four layers, and one rule — source dependencies only ever point inward. The domain knows nothing about the database or HTTP.

LayerFolder.NET equivalentWhat goes here
Domaindomain/Domain projectEntities, value objects, domain services, repository interfaces. Zero imports from other layers.
Applicationapplication/Application project (MediatR handlers)Use cases that orchestrate the domain. Depends only on Domain.
Infrastructureinfrastructure/Infrastructure project (EF Core)SQLite repository, seeding, mapping. Implements the domain interfaces.
APIapi/Web/API project (Controllers)Express wiring, request parsing, validation, calling use cases.

Anemic vs rich: where the rules live

This is the heart of DDD, and the single biggest mindset shift from the POC. In the POC, WorkItem and Resource are plain interfaces — DTOs pretending to be a model — and the rules ("a booked item is locked", "skills must match", "no overlapping bookings") are inline if/throw checks, re-checked in three different functions. Nothing stops a future caller from forgetting one.

POC: anemic

Data is a bag of fields. Logic is a free function that reaches into a global, re-validating the same rules every time. A new code path can skip a check and corrupt state.

Rebuild: rich

The rule lives on the type that owns it. Every path that books a resource goes through Resource.book, and the resource refuses to enter an invalid state. The rule is impossible to skip.

// domain/Resource.ts — the aggregate root guards its own invariants
export class Resource {
  private bookings: Booking[] = [];

  book(workItem: WorkItem, slot: TimeSlot): Booking {
    if (!this.skills.satisfies(workItem.requiredSkills))
      throw new DomainError('Resource does not have the required skills.');
    if (!this.workingHours.contains(slot))
      throw new DomainError('Slot is outside working hours.');
    if (this.bookings.some((b) => b.slot.overlaps(slot)))
      throw new DomainError('Resource is already booked in that slot.');

    const booking = Booking.create(this.id, workItem.id, slot);
    this.bookings.push(booking);
    return booking;
  }
}

The model that falls out, with the rules attached to the types that own them:

The key DDD decisionWhat is the consistency boundary for "no double-booking"? The invariant spans a resource and all of its bookings, so the invariant decides the boundary: Resource owns its bookings as one aggregate. Boundaries are a judgment call, never arbitrary — the rule you must protect tells you where to draw the line.
The rest of the stack, brieflyApplication: one thin use case per action (BookWorkItem), loading aggregates through a repository port — exactly a MediatR handler. Infrastructure: a SqliteWorkItemRepository implementing that port (your IRepository + EF Core). API: a thin route that validates the body with Zod (your FluentValidation) and maps DomainError to a 409. Shared: one shared/ package of wire DTOs + schemas, so client and server cannot drift.
Where this leaves youThe server now owns the data truth, enforces every rule on the type that owns it, and exposes a contract the client can trust. That is the hard half done on home turf. Next: rebuild the client to mirror this cleanly — the three kinds of state, scoped cache invalidation, and the conventions that stop App.tsx from ever becoming a monolith again.
