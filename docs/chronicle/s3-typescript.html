TypeScript in an hour

for typed-language nativesgrounded in domain.ts

You already know a statically typed language. So skip the sales pitch. TypeScript is JavaScript + a type layer that is erased at build time. The types are a compile-time conversation with the compiler; at runtime, it's plain JS and the types are gone. That single fact explains most of its quirks.

This slide teaches TS through the code that's actually in the app. Five differences will surprise a backend engineer, flagged as ⚠ different as we go.

1. Types annotate; inference does the rest

const port = Number(process.env.PORT ?? 3001);  // inferred: number
const initialDate = new Date().toISOString().slice(0, 10);  // inferred: string

function clampInt(value: unknown, fallback: number, min: number, max: number) {
  //                              ↑ you annotate params; return type is inferred
  const parsed = Number(value);
  if (!Number.isFinite(parsed)) return fallback;
  return Math.min(max, Math.max(min, Math.trunc(parsed)));
}

You annotate where the compiler can't guess — mainly function parameters and public boundaries. Locals are usually inferred. ?? is the null-coalescing operator (use the right side only when the left is null/undefined).

2. interface vs type — the shape of data

The domain model uses interface for object shapes. An interface is a named contract for "an object with these fields":

export interface Resource {
  id: string;
  name: string;
  discipline: ResourceDiscipline;   // a union, defined below
  level: ResourceLevel;
  skills: string[];                 // array of strings
  color: string;
  workingHours: { start: number; end: number };  // inline nested shape
}

type does everything interface does and more (unions, tuples, mapped types). Rule of thumb used here: interface for object shapes, type for unions and aliases.

3. Union types — the feature you'll fall in love with ⚠ different

This is the big one. A type can be "one of these exact values." The app uses string-literal unions everywhere instead of enums:

export type Priority = 'Low' | 'Medium' | 'High';
export type WorkItemStatus = 'unscheduled' | 'scheduled' | 'in_progress' | 'completed';
export type ResourceDiscipline = 'Engineer' | 'Data scientist';

// client-side too:
type Theme = 'light' | 'dark';
type AppPath = '/home' | '/schedule' | '/tasks' | '/team';

Now priority = 'Hgih' is a compile error — the typo can't exist. These read like enums but are just strings at runtime, so they serialize over JSON for free and need no import. The whole routing system is built on the AppPath union:

const validPaths: AppPath[] = ['/home', '/schedule', '/tasks', '/team'];

function normalizePath(pathname: string): AppPath {
  return validPaths.includes(pathname as AppPath) ? (pathname as AppPath) : '/home';
}

4. Optional fields and null vs undefined

export interface WorkItem {
  // ...
  assigneeId?: string;   // the ? means "may be absent"
  bookingId?: string;
}

assigneeId?: string means the field is string | undefined. A booked item has one; an open item doesn't. The compiler then forces you to handle the absent case before you use it — no more "cannot read property of undefined" at 2am. The patch handler even distinguishes the two empties deliberately:

assigneeId: hasOwnProperty(body, 'assigneeId')
  ? (body.assigneeId === null ? null : String(body.assigneeId))  // null = "unassign"
  : undefined,                                                    // undefined = "don't touch"

⚠ different JS has two empties. Convention here: undefined = "not provided", null = "explicitly cleared".

5. Record — a typed map/dictionary

const priorityOrder: Record<Priority, number> = { High: 3, Medium: 2, Low: 1 };

Record<K, V> is "an object whose keys are K and values are V." Because K is the Priority union, the compiler checks you've covered every priority — forget Low and it errors. This is how the app sorts by priority without magic numbers scattered around.

6. Generics — types with a hole in them

The pagination envelope is the same shape whether it holds work items or people. So it's generic over its element type T:

export interface Page<T> {
  items: T[];
  total: number;
  page: number;
  pageSize: number;
}

// used two ways, both fully type-checked:
fetchWorkItems(...): Promise<Page<WorkItem>>
fetchResources(...): Promise<Page<Resource>>

One definition, reused with safety intact. Page<WorkItem>.items is a WorkItem[]; Page<Resource>.items is a Resource[]. The paginate<T>() function in scheduling.ts is generic too, so one implementation paginates both. Same idea as generics in any typed language — you'll feel right at home.

7. Narrowing — teaching the compiler what you know

At the HTTP boundary, query params are unknown/string | string[]. You "narrow" them with runtime checks the compiler understands:

const { search, status } = request.query;
queryWorkItems({
  search: typeof search === 'string' ? search : undefined,
  status: typeof status === 'string' ? status : undefined,
});

function parseResourceDiscipline(value: unknown): ResourceDiscipline | null {
  return typeof value === 'string' && disciplines.includes(value as ResourceDiscipline)
    ? (value as ResourceDiscipline)
    : null;
}

Inside the typeof value === 'string' branch, the compiler knows value is a string. This is "control-flow narrowing" — the type changes depending on which branch you're in.

8. The as assertion — a power tool, used sparingly

setData((await response.json()) as BootstrapResponse);  // "trust me, it's this shape"
event.target.value as TaskSort
⚠ A type assertion is a promise, not a checkx as T tells the compiler "treat this as T" without verifying it. response.json() is any at runtime — if the server sends something else, TS won't catch it. Each as is a spot where you've stepped outside the safety net. The rebuild replaces these with runtime validation (e.g. Zod) so the promise is actually checked.

9. Utility types — deriving types from types

function formatResourceRole(resource: Pick<Resource, 'level' | 'discipline'>) { ... }

Pick<Resource, 'level' | 'discipline'> builds a new type with just those two fields. The function honestly advertises "I only need level and discipline" — so you can call it with anything that has those, and the compiler tracks it. (Omit, Partial, Required are the cousins.)

Structural typing: the deepest difference ⚠ different

TypeScript is structurally typed, not nominally. Two types are compatible if their shapes match — names don't matter. The client's WorkItem and the server's WorkItem are different declarations in different files, yet interchangeable because their fields line up. That's why the duplicated types.ts works at all — and also why it's dangerous: nothing forces the two copies to stay in sync. (The rebuild shares one type package so there's only ever one.)

The mental modelThink of TS types as a spec you write next to the code, checked by a relentless reviewer, then thrown away before the program runs. Lean on unions for legal-value sets, generics for reusable shapes, narrowing at every input boundary, and treat every as as a small debt.
