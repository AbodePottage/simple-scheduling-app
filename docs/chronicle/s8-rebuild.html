S8 · the brief

Rebuild: clean + Docker

the redoE2E in one containera weekend

Now you relearn by redoing. Same app, same features, same data model — but built deliberately, with every S7 lesson baked into the structure, and shipped as one self-contained Docker container. This slide is both a target architecture and a brief you can hand to an agent (or work through yourself over two days).

The E2E Docker container

One image: build the client to static files, then let the Express server host both the API and those files (the POC already does this with express.static(clientDist) — reuse it). A multi-stage build keeps the final image small:

# Dockerfile — multi-stage
FROM node:20-alpine AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build              # vite build (client) + tsc (server) + typecheck

FROM node:20-alpine AS run
WORKDIR /app
ENV NODE_ENV=production
COPY --from=build /app/server/dist ./server/dist
COPY --from=build /app/client/dist ./client/dist
COPY --from=build /app/node_modules ./node_modules
EXPOSE 3001
CMD ["node", "server/dist/index.js"]   # serves API + static client on one port
# docker-compose.yml — the whole app in one command
services:
  app:
    build: .
    ports: ["3001:3001"]
    volumes: ["./data:/app/data"]      # SQLite file persists across restarts
docker compose up --build      # → open http://localhost:3001
Why this is the right shapeOne container, one port, both halves inside. No CORS in production (same origin). The SQLite file lives on a mounted volume so data survives docker compose down — the exact debt the in-memory POC couldn't pay. This is "self-contained" in the truest sense: git clone + docker compose up and a stranger has your app running.

A weekend plan

Saturday — backend & contract (the home turf)

  • AM: Stand up shared/domain.ts with types and Zod schemas. Scaffold the server with routes/ + services/ + a Repository interface. Port paginate.ts verbatim.
  • PM: Implement the SQLite repository + seed. Wire the routes, validating input with the schemas. Write a few endpoint tests. You're using S3 (types) and S2 (data flow) the whole time.

Sunday — frontend (the new turf)

  • AM: One feature folder end to end — TasksPage: fetch a page, render the flat list, drop in the kept Pagination. This exercises S4 (JSX lists), S5 (a CSS Module), and S6 (the fetch effect) at once.
  • PM: Repeat the pattern for Home, Team, Schedule. Extract shared bits (Hero, ThemeToggle) as you notice them. Dockerize. docker compose up. Click through. Done.
Order mattersBackend first, on Saturday, on purpose: start where you're strong, lock the contract, then the frontend has a stable thing to talk to. It mirrors the one disciplined arc from the POC — doc → server → client — that produced its cleanest feature.

Definition of done

  • docker compose up --build serves the working app on one port.
  • Data survives a restart (SQLite on a volume).
  • npm run typecheck and tests run in CI; a red type = a red build.
  • No file over ~250 lines; no component owns state it doesn't use.
  • One shared/ type definition; zero blind as on network data.
  • Every list view handles loading, empty, and error states explicitly.

Brief to hand a rebuild agent

Copy-paste starting prompt "Rebuild the simple-scheduling-app with the same features and data model (see docs/chronicle/), but in a clean architecture: a shared/ types+Zod package; an Express server split into routes/services/repository with a SQLite-backed Repository interface and the existing paginate<T>() kept; a React client split into per-feature folders (home/schedule/team/tasks) with CSS Modules and a single tokens.css; keep the Pagination component and Page<T> envelope. Pagination/filtering/sorting are server-side only. Ship it as one multi-stage Docker image that serves API + static client on port 3001, with docker compose up and a persisted SQLite volume. Wire typecheck + tests into CI. Build backend first, then frontend, verifying each layer."
The whole pointYou shipped a rough thing, read its scars, and learned the three browser languages from real code. Now you rebuild it knowing exactly why each clean choice matters — because you felt the cost of its absence. That's the method: learn by doing, relearn by redoing. Go build the second one.
