The rebuild: brief, method & plan

the redoreview every diffordered & shippable

Now you relearn by redoing. Same app, same features, same data model — but built deliberately, with every S7 lesson baked into the structure, and shipped as one self-contained Docker container. This slide is the brief, the method, and the ordered plan for the whole rebuild; the next two go deep on each half — S9 the server, then S10 the client. Use AI to draft each chunk, but review every diff with your own eyes — the review is where the learning happens. The companion lesson breaks the rebuild into small, review-sized chunks with a learning checkpoint for each.

The method: small chunks, strict order, review every diff

For learning, do not just hand off the briefYou could hand this whole brief to an agent and get an app back. Don't. This app is a throwaway training ground; the understanding you carry out is the real artifact. Use AI to go faster, but you read and approve every diff. The agent can type faster than you — only you can understand for you.
  • AI assists, you review. If you cannot explain a line in the diff, you have not learned it yet. Stop and dig in.
  • Small, scoped chunks. A chunk you cannot review in a few minutes is too big. Split it.
  • Strict order. Dependency order means you never review a chunk whose foundation you have not already verified. That is what keeps iteration fast.
  • A verify gate per chunk. Types pass, a test passes, or a route works — before the next chunk begins.

The E2E Docker container

One image: build the client to static files, then let the Express server host both the API and those files (the POC already does this with express.static(clientDist) — reuse it). A multi-stage build keeps the final image small:

# Dockerfile — multi-stage
FROM node:20-alpine AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build              # vite build (client) + tsc (server) + typecheck

FROM node:20-alpine AS run
WORKDIR /app
ENV NODE_ENV=production
COPY --from=build /app/server/dist ./server/dist
COPY --from=build /app/client/dist ./client/dist
COPY --from=build /app/node_modules ./node_modules
EXPOSE 3001
CMD ["node", "server/dist/index.js"]   # serves API + static client on one port
# docker-compose.yml — the whole app in one command
services:
  app:
    build: .
    ports: ["3001:3001"]
    volumes: ["./data:/app/data"]      # SQLite file persists across restarts
docker compose up --build      # → open http://localhost:3001
Why this is the right shapeOne container, one port, both halves inside. No CORS in production (same origin). The SQLite file lives on a mounted volume so data survives docker compose down — the exact debt the in-memory POC couldn't pay. This is "self-contained" in the truest sense: git clone + docker compose up and a stranger has your app running.

The rebuild, in order

Backend first, on purpose: start where you are strong, lock the contract, then the frontend has a stable thing to talk to. Each phase ends on a green gate before the next begins. S9 goes deep on P1–P3 (the server); S10 goes deep on P4–P5 (the client).

Why this orderEach phase produces a stable foundation the next one stands on, so you are never debugging two unfamiliar layers at once. P1 finishing with "zero infrastructure imported" is not a slogan — it is the literal proof that your dependency arrows point the right way.
What a focused weekend looks likeSaturday — backend & contract (home turf): stand up shared/domain.ts with types and Zod schemas, scaffold routes/services/repository, port paginate.ts verbatim, implement the SQLite repo + seed, wire and validate the routes, write a few endpoint tests (that's P0–P3, all S3 types and S2 data flow). Sunday — frontend (new turf): one feature folder end to end (TasksPage: fetch a page, render the list, drop in the kept Pagination — S4 JSX, S5 a CSS Module, S6 the fetch effect at once), then repeat the pattern for Home/Team/Schedule, extract shared bits as you notice them, Dockerize, docker compose up, click through (P4–P5). It mirrors the one disciplined arc from the POC — doc → server → client — that produced its cleanest feature.

Definition of done

Two kinds of done. First the artifact:

  • docker compose up --build serves the working app on one port.
  • Data survives a restart (SQLite on a volume).
  • npm run typecheck and tests run in CI; a red type = a red build.
  • No file over ~250 lines; no component owns state it doesn't use.
  • One shared/ type definition; zero blind as on network data.
  • Every list view handles loading, empty, and error states explicitly.

Then the learning — the part that actually matters here, because you are the real artifact:

  • You can answer the review-lens question for every chunk you accepted — in your own words, without the diff in front of you.
  • You can point at any business rule and name the one type that owns it.
  • You can explain, for any piece of client state, why it is server, UI, or URL state.

Driving the rebuild yourself

Work one small chunk at a time, in the order from the companion lesson (contract → domain → app+infra → API → one client feature → the rest). Let AI draft a chunk, then read the whole diff before you accept it: if you cannot explain a line, you have not learned it yet. A useful per-chunk prompt:

Per-chunk prompt (you review the result) "Implement only this chunk of the simple-scheduling-app rebuild: [the one chunk]. Match the clean architecture from docs/chronicle/: a shared/ types+Zod package; an Express server split into domain/application/infrastructure/api with a SQLite-backed Repository and the existing paginate<T>() kept; a React client of per-feature folders with CSS Modules and one tokens.css; keep the Pagination component and Page<T> envelope; pagination/filtering/sorting server-side only. Show me the full diff and stop. Do not move to the next chunk."
