Architecture & data flow

monorepoSPA + RESTin-memory state

The big picture

It's a classic single-page app (SPA) talking to a REST API. Two halves, one language:

As a backend engineer, the server half will feel like home: routes, handlers, JSON. The new muscle is the client half — a long-lived program running in the browser that keeps its own copy of the data and re-paints the screen when that copy changes.

The data model is the contract

Everything starts from server/src/domain.ts. These types are the single source of truth that both halves agree on:

export interface WorkItem {
  id: string;
  title: string;
  description: string;
  priority: Priority;            // 'Low' | 'Medium' | 'High'
  durationMinutes: number;
  requiredSkills: string[];
  targetDate: string;            // ISO date
  status: WorkItemStatus;        // 'unscheduled' | 'scheduled' | ...
  assigneeId?: string;           // optional → only when booked
}

The client keeps a near-identical copy in client/src/types.ts. That duplication is a smell — S8 shares one package instead — but it shows the principle: the types are the API contract. When the client expects assigneeId and the server stops sending it, TypeScript complains before the user ever sees a bug.

The backend: in-memory state

There is no database. scheduling.ts holds a module-level object and mutates it:

// scheduling.ts (shape)
export const state: AppState = {
  resources: [...seeds],   // 8 people
  workItems: [...seeds],   // 60 work items
  bookings: [],
  skills: [...],
};

export function createWorkItem(input) { state.workItems.push(...); return item; }
export function bookWorkItem(workItemId, resourceId) { /* mutate state */ }
Trade-offIn-memory state means zero setup and data resets on every restart. Perfect to learn on; unacceptable for anything real. The rebuild swaps this one module for a repository interface backed by SQLite — the routes don't change.

Query, filter, paginate — on the server

The interesting backend logic is queryWorkItems: it filters, sorts, then slices a page. The key safety move is clamping — never trust the page number in the URL:

function clampInt(value, fallback, min, max) {
  const n = Number(value);
  if (!Number.isFinite(n)) return fallback;
  return Math.min(max, Math.max(min, Math.trunc(n)));
}

function paginate<T>(items: T[], page: number, pageSize: number): Page<T> {
  const total = items.length;
  const lastPage = Math.max(1, Math.ceil(total / pageSize));
  const safePage = Math.min(page, lastPage);          // ?page=999 → last page
  const start = (safePage - 1) * pageSize;
  return { items: items.slice(start, start + pageSize), total, page: safePage, pageSize };
}

total is computed before slicing, so it always reflects the full filtered set — that's what powers "Showing 11–20 of 40". The server returns the corrected page, and the client trusts it. (This is the heart of the pagination pivot in S7.)

The data-flow loop: how a click becomes a re-render

This is the mental shift from backend work. The app uses one simple, slightly blunt pattern: mutate on the server, then re-fetch everything.

// App.tsx — the whole sync mechanism
const load = async () => {
  const response = await fetch('/api/bootstrap');
  setData((await response.json()) as BootstrapResponse);
};
useEffect(() => { void load(); }, []);   // run once on mount
Server brain vs client brainOn the server, a request handler runs, returns, and forgets. In the browser, the app stays alive. data is a long-lived variable; calling setData(...) is what tells React "the world changed, re-draw." You don't touch the DOM yourself — you change state and React reconciles the screen.

"Re-fetch the whole bootstrap after every change" is deliberately naive. It keeps the client trivially correct (no clever cache to get wrong) at the cost of over-fetching. Pagination later broke from this — the Tasks and Team pages fetch their own slice instead. Knowing when to leave the simple pattern is a judgment call you'll meet again in S6.

The dev setup: two servers, one origin

npm run dev runs both halves at once (via concurrently): Vite on :5173 and the API on :3001. Vite proxies /api/* to the backend so the browser thinks everything is one origin (no CORS pain in dev):

// vite.config.ts
server: { proxy: { '/api': 'http://localhost:3001' } }
ScriptDoes
npm run devVite (client, hot reload) + tsx watch (server, auto-restart)
npm run buildvite build (bundles client) then tsc (type-checks + compiles server)
npm run typechecktype-checks both halves — the only thing that checks the client's types
Gotcha that bit this buildvite build uses esbuild, which strips types without checking them. So a client type error can ship a green build. Always run npm run typecheck — it's the only client type gate. The rebuild wires this into CI.

The monolith: one 1,676-line component

The whole UI lives in a single App.tsx: routing, all four pages, every popup, every form, every handler. It grew organically — and it's the app's biggest structural debt.

Why it happened

Each feature was "just one more block in the file I'm already in." No single commit felt big enough to justify splitting. That's how monoliths are born — one reasonable decision at a time.

Why it hurts

It's why 22629fb was a 1,692-line diff: unrelated concerns share a file, so changes can't stay small. Merge conflicts, hard reviews, scary edits.

Only one component was ever extracted — Pagination.tsx — and notice how clean it is: it takes props, returns markup, owns no app state. That's the template the rebuild applies to everything: HomePage, TaskList, TeamColumn, WorkItemForm, each in its own file.

TakeawayThe architecture is sound in the large (SPA + REST + shared types) and messy in the small (one giant component, duplicated types, naive re-fetch). That split — right shape, wrong granularity — is the single most common state of a fast POC, and exactly what a clean rebuild fixes.
